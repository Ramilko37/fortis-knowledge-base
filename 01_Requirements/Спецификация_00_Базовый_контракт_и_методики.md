# Спецификация 00: базовый контракт и методики расчёта

**Статус:** предложена 2026-07-13.
**Зависимости:** [[ТЗ_Картографическая_модель_защиты]], [[Продуктовый_план_Fortis]], [[03_Architecture/ADR-0005-defense-project-placement-authority|ADR-0005]], [[03_Architecture/ADR-0010-frontend-backend-auth-project-boundary|ADR-0010]].

## Цель

Создать единый, проверяемый фундамент для всех последующих модулей ТЗ. Результаты 2D-карты, калькулятора, отчёта, ретроспективного анализа и моделирования должны ссылаться на одну версию проекта и одни и те же исходные данные.

## Обязательные решения до реализации расчётов

1. Владелец расчётной методики утверждает формулы покрытия, РЭМС, влияния барьеров, вероятностей обнаружения/подавления/поражения и шкалу healthbar.
2. Для каждого входного набора данных фиксируются источник, дата, версия, единицы измерения, точность и статус: `confirmed`, `estimated` или `demo`.
3. Для геометрии фиксируются система координат, допустимая точность, правила преобразования и политика хранения исходных геоданных.
4. Для бюджета утверждается единая политика: превышение блокируется либо допускается только после явного подтверждения с аудитной записью.

До утверждения методики UI может показывать только явно помеченный результат `demo`/`estimated`, но не вероятности, конфликты или healthbar как достоверный расчёт.

## Канонические границы

- `DefenseProject` остаётся единственным источником правды для эшелонов, размещений и выбранной библиотеки.
- Backend хранит версионированный проект и выполняет авторитетные проверки; frontend не подменяет их локальными mock-результатами для server-backed проекта.
- Локальный draft допустим только как recovery-механизм и никогда не перезаписывает серверный проект без явного действия пользователя.
- Каждый расчётный ответ несёт `projectId`, `projectVersion`, `calculationVersion`, `inputDataVersions` и список предупреждений.

## Сквозной контракт проверки

Для любого действия, меняющего проект, backend возвращает:

```ts
type EvaluationStatus = "allowed" | "warning" | "blocked";

type EvaluationResult = {
  projectId: string;
  projectVersion: number;
  status: EvaluationStatus;
  reasons: Array<{
    code: string;
    severity: "info" | "warning" | "error";
    objectIds: string[];
    geometryIds: string[];
    message: string;
  }>;
  calculationVersion: string;
};
```

`warning` не отменяет сохранение, если это разрешено политикой бюджета; `blocked` не изменяет серверную версию проекта. Все причины должны быть пригодны для карты, инспектора и отчёта без преобразования текста во frontend.

## Матрица соответствия и проверки

Для каждого пункта [[ТЗ_Картографическая_модель_защиты|исходного ТЗ]] создаётся запись: требование, владелец репозитория, API/модель, UI-сценарий, fixture и автоматическая проверка. Матрица живёт рядом с реализационными спецификациями и не помечает пункт закрытым без доказательства на server-backed проекте.

## Критерии приёмки

- Один сохранённый проект воспроизводимо даёт одинаковые значения карты, стоимости и отчёта на одинаковой версии входных данных.
- `409 Conflict` не теряет пользовательские изменения: пользователь видит версию, различия и осознанно выбирает reload либо создание нового варианта.
- Тестовый проект с фиксированными fixture покрывает API, frontend integration и E2E-сценарий.
- В knowledge-base опубликованы утверждённые методики и журнал их версий.
