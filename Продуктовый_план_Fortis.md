# Продуктовый план Fortis: GIS MVP

**Дата актуализации:** 2026-06-12  
**Последнее обновление:** backend P1 API — 4 тикета closed 12.06.2026

## Scope decision

MVP Fortis по входящему ТЗ заказчика — это:

- **Модуль геоинформационной системы (ГИС) и построения цифровой модели защиты.**

Из MVP сознательно исключены:

- модуль ретроспективного анализа атак;
- модуль сценарного моделирования.

Эти направления не удаляются из долгосрочного видения, но не входят в ближайший roadmap и не должны влиять на P0/P1-приоритеты ГИС-модуля.

## Коротко

Fortis — это ГИС-конструктор защиты объекта от БПЛА. Пользователь собирает цифровую модель защиты на карте:

- объект → карта → эшелоны → библиотека средств → размещение → зоны покрытия → ограничения → стоимость → сравнение конфигураций → отчёт

Первый MVP строится вокруг 2D-карты. 3D остаётся целевым направлением цифровой модели, но не блокирует поставку 2D MVP.

Основной маршрут расчёта — `/calculator/`. Маршрут `/calculate/` не является критическим путём продукта.

## МОГ как составной объект и демо-акцент

В рамках первого демо МОГ — главный показательный тип объекта, потому что в ТЗ вокруг него описаны люди, оснащение, оружие, сектор применения, ограничения по жилым зонам и стоимость.

МОГ **не является отдельным эшелоном**. Эшелоны отвечают за структуру защиты и дистанцию от объекта, а МОГ является типом средства/поста внутри подходящего эшелона, чаще всего в эшелонах огневого поражения или резерва.

Продуктовая модель МОГ:

- МОГ отображается как отдельный тип защиты и фильтр видимости на карте;
- МОГ размещается на карте как составной `PlacedDefenseObject`;
- карточка МОГ содержит состав группы, тип поста, подотчётность, оснащение, оружие, количество, азимут/сектор, дальность и стоимость;
- покрытие МОГ строится не от абстрактной группы, а от выбранного оружия/оснащения;
- стоимость МОГ считается как сумма состава, оружия и оснащения;
- отчёт должен показывать МОГ не как generic asset, а как пост с составом и вооружением.

Для демо на 2026-06-16 МОГ должен быть героем сценария: пользователь выбирает эшелон, размещает МОГ, задаёт минимальный состав/вооружение, видит сектор поражения, стоимость и попадание в отчёт.

Ограничение "МОГ нельзя стрелять в сторону жилых зон" фиксируется как важное P2-требование. В демо допускается показать warning-заготовку без полноценного географического conflict engine.

## Единая модель проекта

Единый источник правды для пользовательской конфигурации:

- `DefenseProject.layers`
- `DefenseProject.placedObjects`
- `DefenseProject.assetLibrary`

Любое размещение на карте должно становиться объектом `PlacedDefenseObject` в `DefenseProject`.

Изменение объекта должно сразу отражаться:

- на карте;
- в списке объектов эшелона;
- в калькуляторе;
- в печатном отчёте.

`useDefenseStudioStore` остаётся для 3D/demo-runtime-слоёв, но **не** используется как основная модель расчётных размещений.

## P1 — соответствие первому этапу ТЗ по ГИС-модулю

Цель: 2D MVP должен закрывать основные требования заказчика к модулю ГИС и цифровой модели защиты.

### Управление слоями и видимостью

- [ ] Слои по эшелонам:
  - обнаружение и классификация;
  - подавление;
  - огневое поражение;
  - огневое поражение, резерв.
- [ ] Слои по типам защиты:
  - системы обнаружения;
  - РЭБ;
  - МОГ;
  - огнестрельные установки, ЗАК/ЗРК/ПЗРК/ЗРПК и другие средства поражения;
  - сложные установки, состоящие из нескольких блоков.
- [ ] МОГ показывается как тип защиты/фильтр видимости, но не как отдельный эшелон.
- [ ] Управление видимостью:
  - видимость каждого эшелона;
  - видимость типа защиты;
  - видимость отдельной установки.

### Размещение и редактирование объектов

- [ ] Редактирование размещённого объекта:
  - количество;
  - координаты;
  - азимут/направление;
  - статус;
  - перенос между эшелонами.
- [ ] Размещение сложных установок:
  - обнаружение + РЭБ;
  - обнаружение + огневое поражение;
  - другие составные комплексы как единая карточка с несколькими зонами действия.
- [x] Сохранение конфигураций (backend: FRT-29, FRT-30, FRT-31, FRT-39 — 12.06.2026):

  - назвать вариант конфигурации.
- [ ] UI сохранения/загрузки конфигураций (frontend).

### Покрытие

- [ ] Режим «Покрытие»:
  - показать/скрыть покрытие выбранного объекта;
  - показать/скрыть покрытие всех объектов;

- [ ] Поддержать формы покрытия:

  - сектор по азимуту;

### Стоимость и бюджет

- [ ] Считать общую стоимость конфигурации.

  - показывать остаток бюджета;
  - не позволять добавить объект, если он превышает остаток бюджета, либо явно требовать подтверждение исключения, если заказчик выберет мягкий режим.

Критерий P1:

- Пользователь может собрать, сохранить и выгрузить 2D-карту защиты по требованиям первого этапа ТЗ: с эшелонами, типами средств, зонами покрытия, стоимостью, карточками установок и отчётом.

## P2 — ограничения, конфликты и географические барьеры

Цель: карта должна не только хранить объекты, но и подсвечивать ограничения применения.

- [ ] Модель препятствий:
  - жилые зоны;
  - леса;
  - высотность/рельеф;
  - застройка и другие барьеры.
- [ ] Ограничения применения:
  - МОГ нельзя стрелять в сторону жилых зон;
  - РЛС может работать в сторону жилых зон, если нет другого ограничения;
  - разные правила для разных типов средств.
- [ ] Conflict engine:
  - радиоэлектронная совместимость;
  - конфликт направлений/секторов;
  - дубль или перегрузка позиции;
  - объект вне допустимого эшелона;
  - превышение бюджета в hard-limit режиме.
- [ ] Отображение конфликтов:
  - на маркере;
  - в карточке объекта;
  - в панели эшелона;
  - в калькуляторе;
  - в отчёте.
- [ ] Terrain warnings:
  - предупреждение по объекту;
  - предупреждение по покрытию;
  - предупреждение в отчёте.

Критерий P2:

- Пользователь видит, почему конкретное размещение допустимо, рискованно или запрещено, и может исправить конфигурацию до выгрузки отчёта.

## Future scope вне GIS MVP

Эти модули не входят в текущий MVP-roadmap:

- ретроспективный анализ атак;
- сценарное моделирование;
- библиотека профилей БПЛА для симуляций;
- вероятностные расчёты обнаружения/подавления/поражения;
- healthbar боевой устойчивости предприятия;
- анализ «точки невозврата».

Возвращаться к ним стоит только после закрытия P1 или отдельного решения заказчика о расширении scope.

## Проверочный сценарий GIS MVP

- открыть `/prototype/`;
- выбрать предприятие/объект;
- выбрать эшелон;
- выбрать МОГ в библиотеке средств;
- разместить МОГ на карте;
- настроить тип поста, личный состав, подотчётность, оружие, количество и азимут/сектор;
- проверить маркер и зону покрытия;
- открыть список объектов эшелона;
- проверить карточку объекта;
- изменить количество/координаты/азимут;
- включить/выключить видимость объекта, эшелона и типа защиты;
- перейти в `/calculator/`;
- проверить стоимость, структуру и бюджетный остаток;
- сформировать отчёт;
- очистить конфигурацию и проверить пустое состояние без старых бюджетных данных.

## Assumptions

- Ближайший MVP — frontend-first 2D GIS, без полноценного backend collaborative editing.
- Backend потребуется для пользовательских доступов, предприятий, совместного редактирования, документов карточек и durable server-side storage.
- 3D не является блокером первого MVP, но архитектура не должна мешать будущей цифровой 3D-модели.
- Бюджетный hard limit указан в ТЗ, но финальный UX может быть hard-block или soft-confirmation после согласования с заказчиком.
- Ретроспективный анализ и сценарное моделирование не участвуют в приоритизации P0/P1.
- МОГ является главным демо-акцентом первого GIS-среза, но не меняет модель эшелонов: это составной объект/тип защиты внутри `DefenseProject`.
